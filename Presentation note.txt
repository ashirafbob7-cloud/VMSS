QUESTION 01: What is Object-Oriented Programming (OOP), and why did we choose it over procedural
             programming for the VSMM application?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  Procedural programming organizes code into step-by-step lists of instructions and functions that
  manipulate global data. As software grows, procedural code becomes tangled ("spaghetti code") where
  a change in one place breaks unrelated features.
  OOP organizes software into self-contained "objects" that bundle both state (data/attributes) and
  behavior (methods/functions). This mirrors real-world automotive garage operations: cars, mechanics,
  invoices, and spare parts are distinct entities with their own rules.

* WHERE IT IS USED IN VSMM:
  - Model Package: com.vehicleservice.model
  - Every real-world entity is a dedicated class: Vehicle.java, Customer.java, Mechanic.java,
    ServiceRecord.java, SparePart.java, Review.java.
  - Instead of passing raw strings and arrays between functions, our UI and services pass rich domain
    objects like ServiceRecord across the entire architecture.

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "We adopted OOP because an automotive service center is inherently object-oriented. By modeling
  Vehicles, Customers, Mechanics, and Invoices as discrete objects, we achieved modularity, eliminated
  code duplication, and made the system scalable for future garage expansions without rewriting core logic."

QUESTION 02: What is Encapsulation, and how is it implemented across our domain models?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  Encapsulation is data hiding and protection. It means making class variables (fields) private so
  that outside classes cannot tamper with them directly. The only way to read or modify data is through
  public getter and setter methods. This prevents external code from putting invalid data into an object.

* WHERE IT IS USED IN VSMM:
  - All domain models in package com.vehicleservice.model:
    * Vehicle.java: private fields licensePlate, make, model, currentMileage, customerId.
    * Customer.java: private fields customerId, name, phone, email, status.
    * ServiceRecord.java: private fields serviceId, vehicleId, laborCost, partsCost.
  - Access is mediated strictly via public methods like getLicensePlate() and setLicensePlate(String).

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "Encapsulation safeguards internal object state. If fields were public, any UI button or background
  thread could set a vehicle's mileage to a negative number or wipe out an invoice total. By keeping fields
  private and providing validated accessors, we preserve strict data integrity."

QUESTION 03: What are "Domain Guardrails" in Encapsulation, and where are they enforced in code?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  Standard setters simply assign a value (this.x = x). A "Domain Guardrail" adds business logic and
  validation inside the setter or constructor. If someone attempts to pass illegal data (such as a negative
  price or a mileage that goes backward), the method rejects the input with an IllegalArgumentException.

* WHERE IT IS USED IN VSMM:
  - Vehicle.java (line 62):
    public void setCurrentMileage(int mileage) {
        if (mileage < 0) throw new IllegalArgumentException("Mileage cannot be negative.");
        if (mileage < this.currentMileage)
            throw new IllegalArgumentException("Odometer reading cannot decrease from " + this.currentMileage);
        this.currentMileage = mileage;
    }
  - ServiceRecord.java (line 110):
    Guardrails ensure labor cost and parts cost are never negative numbers.
  - SparePart.java:
    Ensures unitPrice >= 0 and quantityInStock >= 0.

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "Encapsulation in VSMM is active, not passive. In Vehicle.java, our setter enforces real-world physics:
  an odometer reading cannot decrease. If an examiner enters -50 km or 10,000 km after 20,000 km, the
  system blocks the entry immediately."

QUESTION 04: What is Abstraction, and how does it differ from Encapsulation?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  - Encapsulation hides DATA (keeping fields private and providing getters/setters).
  - Abstraction hides COMPLEXITY (exposing only essential operations while hiding how they work).
  Think of driving a car: you step on the accelerator pedal (abstraction). You do not need to know how
  the electronic fuel injection, throttle body, and cylinders calculate the stoichiometric fuel-air ratio.

* WHERE IT IS USED IN VSMM:
  - Abstract Class: com.vehicleservice.model.Vehicle
    Hides vehicle classification complexity while exposing calculateServiceMultiplier().
  - Interface: com.vehicleservice.model.Payable
    Hides tax math, labor calculation, and discounts behind calculateTotalCost().
  - Service Facade: com.vehicleservice.service.ServiceCenterManager
    The GUI calls manager.bookService(...) without knowing whether the record is saved to MySQL or CSV.

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "Encapsulation bundles data and safeguards it from illegal access; Abstraction defines high-level
  contracts so callers interact with clean interfaces without worrying about underlying algorithmic details."

QUESTION 05: When should an engineer use an Abstract Class versus an Interface? Give examples.
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  - Abstract Class: Use when classes share an "IS-A" relationship and common code/fields. An abstract
    class can have instance variables, non-abstract methods with code, and constructors.
  - Interface: Use when classes share a "CAN-DO" capability across completely unrelated hierarchies.
    An interface defines a pure behavioral contract (methods to be implemented) with no state.

* WHERE IT IS USED IN VSMM:
  - Abstract Class: Vehicle.java
    Car, Motorcycle, and Truck are all Vehicles ("IS-A"). They share fields like licensePlate, make,
    model, and mileage. Vehicle provides shared constructor logic and common getters.
  - Interface: Payable.java
    ServiceRecord implements Payable ("CAN-DO"). In future iterations, SparePartSale or TowingInvoice
    could also implement Payable even though they are not service records.

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "We used abstract class Vehicle because Cars, Trucks, and Motorbikes share common physical attributes
  and state. We used interface Payable because billing is a capability that can belong to any payable
  entity, maintaining decoupling."

QUESTION 06: What is the `Vehicle` abstract class, and what contract does it enforce?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  Vehicle is an abstract blueprint. You can never create an object of type "Vehicle" directly
  (you cannot write 'new Vehicle()') because an abstract vehicle does not exist in reality; you can only
  instantiate concrete vehicles like a Toyota Land Cruiser (Car) or a Scania R500 (Truck).
  Vehicle forces every subclass to define its own specific behavior through abstract methods.

* WHERE IT IS USED IN VSMM:
  - File: src/main/java/com/vehicleservice/model/Vehicle.java
  - Abstract Methods enforced on subclasses:
    1. public abstract double calculateServiceMultiplier();
    2. public abstract int getRecommendedServiceIntervalKm();
    3. public abstract List<String> getSpecializedInspectionItems();
    4. public abstract String getVehicleType();
    5. public abstract String getSpecificAttributeLabel();
    6. public abstract String getSpecificAttributeValue();

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "Vehicle enforces architectural conformity. Any developer adding a new vehicle type—such as ElectricBus—is
  forced by the Java compiler to supply a service multiplier, an inspection checklist, and an interval,
  preventing incomplete vehicle definitions."

QUESTION 07: What is the `Payable` interface, and why is it crucial for financial abstraction?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  The Payable interface defines a financial contract. Any class that implements Payable promises to
  calculate its subtotal, apply taxes, compute the final balance, and generate an itemized invoice.
  The billing system only cares that an entity is "Payable"—it does not care whether it is an oil change,
  an engine replacement, or a fleet lease.

* WHERE IT IS USED IN VSMM:
  - File: src/main/java/com/vehicleservice/model/Payable.java
  - Contract Methods:
    * double calculateSubtotal();
    * double calculateTax();
    * double calculateTotalCost();
    * String generateInvoiceSummary();
  - Implemented by: com.vehicleservice.model.ServiceRecord.java (line 21)
    ServiceRecord calculates parts cost + labor cost, multiplies by the vehicle's specific multiplier,
    adds 18% URA VAT, and formats the output into Ugandan Shillings (UGX).

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "Payable decouples billing from maintenance. Our PaymentDialog and InvoiceDialog interact with Payable
  references. If AutoCare introduces parts-only over-the-counter sales tomorrow, we just implement
  Payable on CounterSale without altering the checkout GUI."

QUESTION 08: What is Inheritance, and what class hierarchies exist in VSMM?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  Inheritance allows a subclass ("child") to inherit attributes and methods from a superclass ("parent").
  This promotes code reuse, avoids copy-pasting code, and creates clear hierarchical classification.

* WHERE IT IS USED IN VSMM:
  - Hierarchy 1: Vehicle -> Car, Motorcycle, Truck
    * Car.java extends Vehicle: adds carType (SEDAN, SUV, COUPE), doorCount, isHybrid.
    * Motorcycle.java extends Vehicle: adds engineCapacityCc, bikeType (BODA_BODA, SPORT, CRUISER), hasHelmetBox.
    * Truck.java extends Vehicle: adds cargoCapacityTons, axleCount, hasAirBrakes.
  - Hierarchy 2: Person -> Customer, Mechanic
    * Person.java defines shared human identity: id, name, phone, email.
    * Customer.java extends Person: adds customerType (RETAIL, CORPORATE, VIP) and vehicle registry.
    * Mechanic.java extends Person: adds specialization (ENGINE, BRAKES, ELECTRICAL), hourlyRate, status.

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "Inheritance in VSMM eliminates over 400 lines of redundant code. Customer and Mechanic inherit common
  fields from Person, while Car, Motorcycle, and Truck inherit registration and odometer logic from Vehicle."

QUESTION 09: What does the `super` keyword do, and where is it used in constructors and methods?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  The `super` keyword in Java refers directly to the immediate parent (superclass).
  1. super(...) calls the parent constructor to initialize inherited fields.
  2. super.methodName() invokes the parent's version of an overridden method.

* WHERE IT IS USED IN VSMM:
  - Car.java (constructor):
    public Car(String vehicleId, String licensePlate, String make, String model, int year,
               int currentMileage, String customerId, CarType carType, int doorCount, boolean isHybrid) {
        super(vehicleId, licensePlate, make, model, year, currentMileage, customerId);
        this.carType = carType;
        this.doorCount = doorCount;
        this.isHybrid = isHybrid;
    }
  - Mechanic.java (constructor):
    Calls super(id, name, phone, email) to let Person initialize the base contact details.

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "In Car.java, calling super(...) ensures that base vehicle properties like license plate and odometer
  are initialized properly according to the encapsulation rules of Vehicle before Car sets its own fields."

QUESTION 10: What is Polymorphism, and what is the difference between Compile-Time and Runtime?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  Polymorphism means "many forms" (Greek: poly = many, morph = form). It allows the same method call
  to produce different behaviors depending on the actual object being invoked.
  - Compile-Time Polymorphism (Method Overloading): Multiple methods in the same class share the same
    name but have different parameter lists. Resolved at compile time.
  - Runtime Polymorphism (Method Overriding): A subclass provides its own specific implementation of a
    method defined in its parent class. Resolved dynamically at execution time.

* WHERE IT IS USED IN VSMM:
  - Overloading (Compile-Time):
    * UIUtils.createSectionHeader(title, description) vs createSectionHeader(title, description, isDark).
    * NotificationObserver.dispatch(recipient, channel, message) vs dispatch with 8 parameters.
  - Overriding (Runtime):
    * calculateServiceMultiplier() is overridden in Car, Motorcycle, and Truck.

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "Compile-time polymorphism gives callers flexible convenience methods, while runtime polymorphism
  enables dynamic method dispatch where the Java Virtual Machine decides which pricing multiplier to run."

QUESTION 11: How does Dynamic Method Dispatch work when calculating service costs for different vehicles?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  Dynamic Method Dispatch is the JVM runtime mechanism that invokes an overridden method based on the
  actual object type created in memory (the right-hand side of 'new'), not the reference type.
  When ServiceRecord calculates labor cost, it calls `vehicle.calculateServiceMultiplier()`. ServiceRecord
  does not know or care if the vehicle is a Truck, a Motorcycle, or a Car—the JVM automatically routes the
  call to the correct subclass at runtime.

* WHERE IT IS USED IN VSMM:
  - Car.java (line 42):
    Returns 1.0x (standard) or 1.15x for complex hybrid drivetrains.
  - Motorcycle.java (line 38):
    Returns 0.8x (discounted labor for compact boda-bodas).
  - Truck.java (line 44):
    Returns 1.7x (70% heavy-duty surcharge for commercial trucks with air brakes).
  - ServiceRecord.java (line 124):
    double laborCost = baseLaborRate * vehicle.calculateServiceMultiplier();

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "This is pure OOP elegance. There is no ugly switch(vehicleType) statement in ServiceRecord. If an
  examiner asks how adding a 'Tractor' would affect the billing engine, the answer is: zero changes to
  ServiceRecord. We simply subclass Vehicle and override calculateServiceMultiplier() to return 2.2x."

QUESTION 13: Why are design patterns used in software engineering, and which ones are implemented in VSMM?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  Design patterns are battle-tested, reusable architectural solutions to commonly occurring software
  engineering problems. Rather than reinventing the wheel with ad-hoc code, engineers use patterns
  established by the Gang of Four (Erich Gamma, Richard Helm, Ralph Johnson, John Vlissides).

* WHERE IT IS USED IN VSMM:
  VSMM implements five distinct GoF Design Patterns:
  1. Strategy Pattern: Mechanic Assignment & Payment Gateways.
  2. Decorator Pattern: Dynamic Service Pricing & Add-on Decorators.
  3. Observer Pattern: Event Publisher, Telecom SMS Gateway & CSV Security Audit Trail.
  4. Facade Pattern: Unified subsystem coordination via ServiceCenterManager.
  5. Factory Pattern: Vehicle parsing and instantiation via VehicleFactory.

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "Design patterns make our codebase maintainable, testable, and compliant with SOLID principles.
  For example, our pricing adheres to the Open/Closed Principle: open for extension with new discounts,
  closed for modification of base calculation logic."

QUESTION 14: What is the Strategy Pattern, and how is it used for Mechanic Assignment?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  The Strategy Pattern defines a family of interchangeable algorithms, encapsulates each one inside a
  class, and makes them swappable at runtime. The client uses an algorithm through an interface without
  knowing its internal mechanics.

* WHERE IT IS USED IN VSMM:
  - Package: com.vehicleservice.assignment
  - Interface: MechanicAssignmentStrategy.java
    public AssignmentResult assignMechanic(ServiceRecord record, List<Mechanic> mechanics, Vehicle vehicle);
  - Concrete Strategies:
    1. SkillMatchStrategy: Matches technician expertise to vehicle type and service package.
    2. WorkloadBalancingStrategy: Assigns the available technician with the fewest active jobs.
    3. RatingBasedStrategy: Routes VIP vehicles to mechanics with the highest customer star ratings.
    4. RoundRobinStrategy: Distributes intake jobs in a fair, cyclical roster.

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "In ServiceBookingDialog, the garage administrator can select which assignment strategy to use via a
  dropdown. The system switches from workload balancing to skill matching seamlessly at runtime without
  restarting or recompiling the application."

QUESTION 15: How does `SkillMatchStrategy` work in practice?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  Assigning a motorcycle brake repair to a heavy-duty diesel engine specialist is inefficient.
  SkillMatchStrategy inspects the vehicle type (Car, Motorcycle, Truck) and the required service
  (Brake Overhaul, Engine Diagnostics, Transmission Flush) and filters available mechanics who possess
  the exact required specialty.

* WHERE IT IS USED IN VSMM:
  - File: src/main/java/com/vehicleservice/assignment/SkillMatchStrategy.java
  - Logic:
    1. Determines required specialization: e.g., Truck -> HEAVY_VEHICLE; Electrical -> AUTO_ELECTRICS.
    2. Filters list of mechanics by status == AVAILABLE.
    3. Scans mechanic specializations.
    4. If a match is found, returns AssignmentResult(mechanic, true, "Matched specialty: " + spec).
    5. If no exact match is available, falls back to the mechanic with the highest experience years.

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "SkillMatchStrategy enforces workshop safety and competence. It guarantees that specialized jobs—like
  high-voltage hybrid diagnostics or air-brake servicing—are assigned only to certified technicians."

QUESTION 16: How does `WorkloadBalancingStrategy` prevent mechanic burnout and bay bottlenecks?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  In busy repair garages, top mechanics often get overloaded while junior mechanics sit idle.
  WorkloadBalancingStrategy queries active workshop bay allocations and assigns incoming cars to the

  "WorkloadBalancingStrategy solves an operational bottleneck. By evenly distributing repair tickets
  across our 8 workshop bays, we minimize customer wait times and prevent technician fatigue."

QUESTION 18: What is the Decorator Pattern, and why is it superior to multiple boolean flags for pricing?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  The Decorator Pattern attaches additional responsibilities, discounts, or surcharges to an object
  dynamically without modifying its underlying code.
  If you use boolean flags (hasVipDiscount, hasWarranty, isExpress, hasFluids), every calculation requires
  a messy ladder of nested if/else statements. Adding a new discount requires modifying and re-testing
  the entire class. With Decorators, each add-on is an independent wrapper that can be stacked in any order.

* WHERE IT IS USED IN VSMM:
  - Package: com.vehicleservice.pricing
  - Component Interface: ServicePricing.java (declares calculateFinalPrice(basePrice))
  - Concrete Component: BaseServicePricing.java (returns unmodified labor + parts)
  - Abstract Decorator: ServicePricingDecorator.java (wraps a ServicePricing instance)
  - Concrete Decorators:
    * VipDiscountDecorator.java: Applies a 15% discount for VIP customer loyalty.
    * PromotionalDiscountDecorator.java: Deducts a promotional voucher (e.g., UGX 50,000 off).
    * ExtendedWarrantyDecorator.java: Adds a 6-month mechanical warranty surcharge (+UGX 120,000).
    * PremiumSyntheticFluidsDecorator.java: Upgrades engine fluids to Castrol Edge (+UGX 85,000).
    * ExpressPriorityServiceDecorator.java: Bumps vehicle to Bay 1 Priority Queue (+25% rush fee).

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "The Decorator Pattern directly fulfills the Open/Closed Principle. We can combine a VIP discount, an
  extended warranty, and express rush service like stacking Russian nesting dolls—without changing a single
  line in BaseServicePricing."

QUESTION 19: How do `VipDiscountDecorator`, `ExtendedWarrantyDecorator`, and `ExpressPriorityServiceDecorator`
             execute calculation math in a decorator chain?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  When decorators are chained, calling calculateFinalPrice() on the outermost decorator cascades through
  each wrapped decorator until it hits BaseServicePricing, and then unwinds back up, applying fees and
  discounts sequentially.

* WHERE IT IS USED IN VSMM:
  - Code Example (Demonstrated in VehicleServiceTest.java, Test 07):
    ServicePricing pricing = new BaseServicePricing(); // UGX 500,000
    pricing = new ExpressPriorityServiceDecorator(pricing); // +25% -> UGX 625,000
    pricing = new ExtendedWarrantyDecorator(pricing); // +UGX 120,000 -> UGX 745,000
    pricing = new VipDiscountDecorator(pricing); // -15% VIP -> UGX 633,250
    double finalCost = pricing.calculateFinalPrice(500000);
  - Each decorator overrides calculateFinalPrice:
    return wrapped.calculateFinalPrice(basePrice) * 0.85;

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "The execution order is predictable and composable. In JUnit Test 7, we verify that wrapping BaseServicePricing
  with multiple decorators computes the exact expected Ugandan Shilling total down to the cent."

QUESTION 20: What is the Observer Pattern, and why is it considered a decoupled architecture?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  The Observer Pattern defines a one-to-many dependency between objects. When one object (the Subject)
  changes its state, all its registered dependents (Observers) are notified and updated automatically.
  It is decoupled because the Subject only knows that its listeners implement a simple interface
  (ServiceEventListener). The Subject has zero knowledge of what the listeners do with the information.

* WHERE IT IS USED IN VSMM:
  - Package: com.vehicleservice.observer
  - Subject: ServiceEventPublisher.java
    Maintains a list of ServiceEventListener listeners. Exposes addListener() and publishEvent().
  - Observer Interface: ServiceEventListener.java
    void onServiceEvent(ServiceEvent event);
  - Concrete Observers:
    1. NotificationObserver.java: Dispatches role-scoped telecom SMS (MTN/Airtel) and gateway alerts.
    2. AuditLogObserver.java: Appends security compliance records to data/audit_logs.csv.

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "MaintenanceService does not know about SMS gateways or CSV logging. When an order status changes,
  it simply fires an event to ServiceEventPublisher. If we decide to add email or WhatsApp notifications
  tomorrow, we create a new Observer without modifying existing maintenance code."

QUESTION 22: How does `NotificationObserver` route simulated SMS to MTN, Airtel, and Admin?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  When an event occurs, different people need different information:
  - Customer: Needs SMS alerts about their car's progress (booking confirmed, inspection done, invoice paid).
  - Mechanic: Needs alerts about jobs assigned to them, status updates, and customer reviews.
  - Administrator: Needs the master live feed of every activity across the garage.
  NotificationObserver acts as a role-scoped telecom router, creating OutboundNotification objects tagged
  with customer IDs, mechanic names, and vehicle IDs.

QUESTION 28: How does DatabaseManager prevent SQL Injection attacks?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  SQL Injection occurs when malicious user input is concatenated directly into SQL queries
  (e.g., "SELECT * FROM users WHERE user = '" + input + "'"). An attacker could type "' OR '1'='1" to
  bypass passwords or "'; DROP TABLE vehicles; --" to delete tables.
  VSMM uses PreparedStatement with parameterized queries (using '?') everywhere. The database driver treats
  all user inputs strictly as literal data, never as executable SQL commands.

* WHERE IT IS USED IN VSMM:
  - File: src/main/java/com/vehicleservice/storage/DatabaseManager.java
  - Example:
    String sql = "INSERT INTO services (service_id, vehicle_id, customer_id, service_date, service_type, " +
                 "status, labor_cost, parts_cost, notes, technician_name) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?)";
    try (PreparedStatement ps = conn.prepareStatement(sql)) {
        ps.setString(1, s.getServiceId());
        ps.setString(2, s.getVehicleId());
        ps.setString(3, s.getCustomerId());
        ps.setDate(4, java.sql.Date.valueOf(s.getServiceDate()));
        ps.setString(5, s.getServiceType().name());
        ps.setString(6, s.getStatus().name());
        ps.setDouble(7, s.getLaborCost());
        ps.setDouble(8, s.getPartsCost());
        ps.setString(9, s.getServiceNotes());
        ps.setString(10, s.getTechnicianName());
        ps.executeUpdate();
    }

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "Every database query in VSMM uses parameterized PreparedStatements with automatic try-with-resources
  leak prevention, ensuring complete immunity against SQL injection vulnerabilities."

QUESTION 29: What is `DriverShim` and dynamic classloading in `DatabaseManager.java`, and why was it necessary?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  In Apache NetBeans and Maven environments, the JDBC driver (`mysql-connector-j-9.7.0.jar`) is often
  loaded by a different classloader than the application when executed via `mvn exec:java`. When Java's
  `DriverManager.getConnection()` is called, DriverManager refuses to use a driver loaded by a child
  classloader for security reasons, throwing `SQLException: No suitable driver found`.
  A `DriverShim` is an elegant design pattern wrapper that implements `java.sql.Driver` and delegates to
  the dynamically loaded driver, registering it with DriverManager so it works in any execution context.

* WHERE IT IS USED IN VSMM:
  - File: src/main/java/com/vehicleservice/storage/DatabaseManager.java (lines 50-78)
  - Class: private static class DriverShim implements Driver
  - Dynamic loader: Scans project lib directory, creates URLClassLoader, loads com.mysql.cj.jdbc.Driver,
    wraps it in DriverShim, and calls DriverManager.registerDriver(new DriverShim(driver)).

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "This solves a notorious NetBeans/Maven desktop classpath isolation defect. Our self-healing classloader
  guarantees that the MySQL driver is loaded dynamically whether the app is launched from NetBeans IDE,
  command line Maven, or a standalone double-clickable batch script."

QUESTION 41: What is the Swing Event Dispatch Thread (EDT), and why must `SwingUtilities.invokeLater` be used?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:

  race conditions, visual glitches, and freezing. `SwingUtilities.invokeLater(Runnable)` safely queues
  the GUI task onto the EDT.

* WHERE IT IS USED IN VSMM:

    so the badge updates smoothly without thread collisions.

* EXAMINER DEFENSE TIP / KEY TALKING POINT:

  increments—is dispatched through SwingUtilities.invokeLater to guarantee rock-solid stability on the EDT."

QUESTION 43: What was the non-editable `JTextArea` bug in Nimbus dark mode, and how was it permanently fixed?
----------------------------------------------------------------------------------------------------
* CONCEPT EXPLAINED SIMPLY:
  In Nimbus, when `txtArea.setEditable(false)` is set, Nimbus's internal Synth painter automatically
  replaces the component's foreground color with `TextArea[NotEditable].textForeground` (which defaults

  On a dark navy card (`#0c1836`), charcoal text is literally invisible!
  We resolved this by setting `txtArea.setUI(new BasicTextAreaUI())`, which completely bypasses Nimbus's
  Synth painter, and overriding `paintComponent` to dynamically enforce `Color.WHITE` in dark mode.

* WHERE IT IS USED IN VSMM:

  - JTextArea txtMsg in createNotificationCard:

    txtMsg.setDisabledTextColor(isDarkMode ? Color.WHITE : new Color(15, 23, 42));
  - Also applied to txtNotes in CustomerPortalFrame's 3-stage progress pipeline widget.

* EXAMINER DEFENSE TIP / KEY TALKING POINT:
  "This is a demonstration of deep Swing framework expertise. Rather than accepting Nimbus's default
  limitations, we installed a custom BasicTextAreaUI delegate, ensuring 100% crystal-clear, brilliant
  white typography in Cyber-Dark mode."

QUESTION 50: How should group members handle unpredictable or difficult examiner questions?

* CONCEPT EXPLAINED SIMPLY:
  Examiners often ask edge-case or hypothetical questions ("What if we wanted to add electric vehicles?",
  "Why didn't you use Spring Boot?", "What happens if two mechanics grab the same car?").
  Follow the "Acknowledge - Anchor to OOP - Answer with Code" formula:

  1. STAY CALM & ACKNOWLEDGE:
     "That is an insightful question, Professor/Examiner."
  2. ANCHOR TO AN OOP CONCEPT OR PATTERN:
     "Because of our adherence to the Open/Closed Principle and the Strategy Pattern..."
  3. POINT DIRECTLY TO THE FILE:
     "We would handle that in com.vehicleservice.model by simply subclassing..."

  * EXAMPLES OF COMMON TRICK QUESTIONS & MODEL RESPONSES:
    - Q: "Why didn't you use a web framework like Spring Boot or Django?"
      A: "Our project specification required a standalone Java OOP desktop application in Apache NetBeans
         with raw Swing and JDBC. By avoiding heavy web frameworks, we proved that we can implement core
         OOP, GoF patterns, thread safety, and persistence directly in pure standard Java."
    - Q: "What if AutoCare introduces Electric Vehicle (EV) battery servicing?"
      A: "Because of Abstraction and Inheritance, we simply create ElectricCar extending Vehicle, override
         calculateServiceMultiplier() to 1.3x for high-voltage battery labor, and add specialized EV
         inspection items (Battery State of Health, Inverter Cooling). No existing billing code is touched."
    - Q: "What happens if a user inputs text into a numeric price field?"
      A: "All UI dialogs validate inputs inside try-catch blocks handling NumberFormatException, displaying
         friendly error popups without terminating the application thread."

  "Never guess or panic. Anchor your response to the Four Pillars (Abstraction, Encapsulation, Inheritance,
